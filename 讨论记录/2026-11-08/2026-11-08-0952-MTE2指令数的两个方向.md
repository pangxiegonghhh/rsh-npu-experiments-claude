# B 搬运指令数的两个方向：Ascend-SpMM 的 n 与本项目的段数 R

日期：2026-11-08（北京时间 17:52；文件名按 UTC）。接 `讨论记录/2026-11-06/2026-11-06-1140-T23派发.md`。本轮未运行实验，只做文献关系的澄清。

---

## 1. 起因

用户读 Ascend-SpMM 时注意到一句话（§3.4，p5–6）：「对于固定的 k，增大 n 会减少 B 在特征维度上的分块数量。
这减少了 B 的 MTE2 搬运指令数，并通过分摊固定的启动开销提升单条指令的吞吐。」问它与本项目「压低段数 R」的关系。

## 2. 关系：同一个开销的两个方向，正交

B 这块稠密矩阵有两个维度。取一个窗口要用的 B 时：

| | 减少的是哪一维的指令数 | 手段 | 谁做 |
|---|---|---|---|
| N 方向（特征维度，宽度 N） | 每条指令搬得更宽 → N 方向分块数变少 | 调内核分块参数（原文取 n = 1024 FP16 / 512 FP32，每批 g = 6 个归约 tile，MTE2 批量预发） | Ascend-SpMM §3.4 |
| K 方向（要取哪些 B 行） | 让窗口用到的行在编号上挨在一起 → 连续段数变少 | 行重排 / 对称置换（本项目第一层 RQ2） | 本项目 |

**一处口径更正（用户 2026-11-08 的表述里反了，记下来避免写进论文）：** Ascend-SpMM 减少的是 **N 方向**的指令数；
**K 方向**（段数 R）是本项目的部分。两者正交，不是同一维度上的竞争。

## 3. 对本项目的三点用处

1. **前提有了外部旁证。** 「搬运指令条数本身就是代价，因为每条有固定启动开销」是 Ascend-SpMM 自己的原话与实测
   （§3.4「摊薄每条指令的固定启动开销」；Table 1 MTE2 延迟 > 100 ns），不必由本项目论证。审稿人质疑「少几条指令有什么用」时可引。
2. **正交、可叠加。** 它把 N 方向调到最宽之后，K 方向的段数仍只能靠重排压低；原文全文无行重排、无以段数为目标的列置换
   （阅读记录 §1、§3.3 已记）。这与阅读记录 §3.4「第一层与它的映射正交、可组合」是同一结论的另一面。
3. **n 开大时段数的占比更高【推】。** n = 1024（FP16）时 N 方向可能只剩一个块，此时窗口取 B 的指令数几乎全由 K 方向的段数决定。
   若成立，本项目这一项的相对重要性在它的内核上反而更高。

## 4. 不能写成结论的两点（留给 G2 / T8）

1. **「指令数 ≈ N 方向块数 × K 方向段数」只是【推】。** MTE2 支持带 stride 的 ND2NZ 搬运，一条指令是否能跨越若干不连续的行段，
   决定这个乘积关系成立到什么程度。**这正是 G2 要测的**：固定取数总量与 N（取内核实际使用的 n），只改段数，看耗时怎么变。
2. **本项目仍未有 NPU 实测。** 在 G2 的段长–耗时曲线出来之前，上述关系只是「有利旁证 + 推断」，不是本项目自己的证据。
   引用时按阅读记录 §3.3 的口径：Ascend-SpMM 覆盖了 U 的那一半，R 仍是新的。
