## 与原大纲的关系

原大纲（`RSH-NPU主线与ND2NZ后续优化大纲-简版.md`）的分层结构保留。修订点：

- 增加贯穿各层的统一代价模型，作为每层的评价目标。
- 列置换从观察项升为正式变量（用户已同意）。
  - **口径限定。** NeutronSparse 并非不做列置换——全局阶段就把矩阵建模成二分图，用
    Rabbit Order **同时重排行和列**；只有局部阶段是「only permutes rows and does not
    alter the global column order」（§6.1 原文）。所以新意不在「做列置换」这个动作，
    而在它**服务的目标**：NeutronSparse 的全局列置换是为 tile 密度，本项目要的是为 B
    的段数 R。表述上必须写成目标之差，否则易被质疑为已有工作。
  - **正交性。** 列置换不改变列并集基数，只改变列号是否连号。故 U_w 与 R 两项正交，
    并列进统一代价模型成立。合成矩阵上可见：Rabbit 两视图列并集同为 56.42、k16 同为
    3.75，仅段数与段长变化（`method_metrics.csv`）。
  - **归属更正（2026-11-03）：** 上面两条都不是本轮新发现，已有两处记录在先。
    `01` 第 1 条（11-02）已写明「NeutronSparse 的 Global 阶段本来就同时重排行列（§6.1）」，
    并给出 RSH 的权衡数据「窗口平均非零列从 79.8 降到 46，但平均段长从 2.70 降到 1.56」。
    调研第二版 `report.md` §5 末段也写明「Neutron 原论文同时置换行列，列置换对固定行组的
    并集基数不变，但可能改变粗聚类结果、连续段与 B 局部性，因此需保存两种映射」。
    本轮只是用论文原文和 CSV 做了独立复核。调研方还多指出一点前面未展开的：列置换虽不
    改变并集基数，却会**改变 Rabbit 粗聚类的结果**（二部图上行列同排，列序影响社区划分），
    所以必须同时保存原生行序与列序两套映射。
  - **与候选规格的冲突（须在 T1/T3 解决）：** 调研候选规格 `candidates.md` §2「输出」
    明文规定「主比较不应用全局列置换……保留原始列编号计算 U 和 T」，C5 的适配也写了
    「首轮不应用全局列置换」。列置换升为正式变量与这条接口规定直接冲突，必须修改该
    规格的输入输出约定，而不是只在评价器里加一个视图。
  - 第一层原约定「主要比较采用 `row_only` 视图，`native` 仅作补充参考」
    （见 `RSH 行重排结构实验计划草稿` §3）需随之修改，并入 T1 的「对称置换视图」。
- ND2NZ 从"另一条研究线"降为第 5 层的执行选项，是否使用由代价模型和段长分布决定。
- 存储层拆为结构 + 载荷，载荷增加 Dense-NZ 选项。
- "细粒度行划分同时得到窗口集合和残余集合"原大纲已写明，不需改（用户纠正）。

## 判断树

```text
G1：相同 AIC nnz 占比下，流水线 B 的 padding / T 是否明显少于 NeutronSparse？
 ├─ 否 → 上下文感知划分的空间有限，重新找切入点（G2 不用看）
 └─ 是 → G2：B 的段数 R 对供数耗时影响大吗（已计入双缓冲重叠）？
          ├─ 是 → 主线：B 供数代价驱动的划分 + 布局协同设计
          └─ 否 → 主线：上下文感知划分；ND2NZ 只作工程优化
```

**G2 判据的幅度基准（2026-11-03 更正）：** `03` 与 `01` 第 1 条引用的都是**平均段长**
（1.56 → 7.59、2.70 → 1.56），本轮从 `method_metrics.csv` 把段数算出来后更正为：决定搬运
指令数的是**段数 R**，列置换在合成矩阵上把 R 降低 18%–26%（Rabbit 30.17→22.33，
Neutron 29.67→24.42），不是 4.9 倍。平均段长是「窗口内平均」再平均，会被少数长段拉高，
不等于指令数的倒数。

该用 R 这件事本身早有记录：`01` 第 2 条已要求「增加 DMA 次数代理：按『每段一次搬运』和
『每行一次搬运』分别计数」，T1 也列了 R_w。本轮新增的只是**代入数字后的幅度**——指标定了
但没人算过，而 G2 的判断树要的正是这个幅度。因此 G2 应问「R 降两成能换来多少 AIC 时间」，
并扣除 L2 预置（NeutronSparse §6.2.1）已拿走的部分。详细更正与证据强度见 `03`。

## T6 的 Δ 判据方向：从「方向待定」到「可写成式子」（2026-11-03）

**已有结论（`04` 其他需要补的地方，不是本轮新发现）：** 「RSH Algorithm 1 把满足
Δ < τ_inc 且 nz_r ≤ τ_nnz 的行送残余。在 NPU 上 T = ⌈U/K0⌉，Δ 小的行进窗口 K 不变、
只多占一行 M，反而提高密度；按 NPU 代价该送残余的可能是『Δ 大、nnz 少』的行。RSH 的
理由在 GPU 8×8 小块上可能成立，NPU 上应作为流水线 B 的设计变量用实验确定方向。」
方向分析到此已经完备，本轮用 RSH 原文 §3.3.1 复核无误：原文剔除「Δ 小且 nnz 少」行的
理由确实是 tile 密度，加上 CUDA 核处理轻量操作时寄存器压力与调度开销更低，与列并集代价
无关，所以该理由不能平移到 NPU。

**本轮新增的是判据的形式，不是方向。** 补传的 AFH 全文给出一个可直接套用的结构：其 Dense
接受判据（§3.2 acceptance test）是「estimates the number of row-wise 2:4 tiles before and
after removing the candidate columns, and **accepts the dense tile only when it reduces the
remaining sparse-tile cost**」——不以候选自身的局部密度判断取舍，而看**拿走它之后另一条
路径是否更便宜**。AFH 在窗口内按列粒度做，本项目需要在行粒度上跨「窗口 / 残余」做。

于是 T6 不必停在「方向可能反了，待实验确定」，可以直接写成两条路径的代价比较：

- 该行留在 AIC：代价是它带来的 ΔU_w（推高列并集 → L0B 占用、B 取数行数、K 方向块数 T）。
- 该行改走 AIV：代价是 nnz_r × N。

取代价小的一侧。这样方向成为比较式的输出，而不是预设；系数由 G2 与 E3-ext 标定
（载荷为 Dense-NZ 时 A 侧只看 T，为 Bitmap 时还依赖每块 z，见 `05`，故目标函数形式也随
E3-ext 的结论变化）。补读结论把这条列为 F-AFH 的后续层参考，本轮判断它对 T6 当下即适用，
故前移。

**一条配套警示：** AFH 表 3 显示局部密度提高与总块数下降不是一回事——Flan_1565 的 Dense
局部密度改善，总块数相对 pure-2:4 反而增加 4.72%。所以第一层评价必须把「窗口密度改善」与
「Tile 数减少」分开报告，不能用前者推断后者。这与「减少 T 与提高 ρ 不重复计分」是两件事：
那条讲同一收益的两种表达，这条讲两个指标可能反向。

执行顺序：T12 与 T3 须先同轮决定（T1 的口径依赖它）；随后 T1、T2、T4、T5 可马上开始；
T6 → T7 依次进行；T8 与前面并行；T9 并行但须先完成 T13。

**T5 优先级上调（2026-11-03）：** 第一层原定首轮候选矩阵为 cora、wiki-RfA、dawson5、
olafu、pattern1、human_gene1 六张，**不含 ogbn-arxiv**；而 `02` 关于「静态阈值在 GNN 图上
基本不起作用」的论证整个建立在 ogbn-arxiv 上。所以 T5 不是补充数据集，而是补上论证所
依赖的那张矩阵，应与 T1、T2 同级甚至更前。

**第一层已有数据的现状：** Cora 先导实验在实例上跑通（加载后 2708×2708、10,556 NNZ，
8 个方法/视图正确性检查通过），但证据包留在实例 `/data/rsh-neutron-upload/` 与
`/data/rsh-cora-pilot-evidence.tar.gz`，本轮整理未取回、未重新核验，**不算已归档结果**。

## T11 的依据（2026-11-03 核对 RSH 原文）

Algorithm 1 第 20–21 行：判据通过时提交整个窗口 `[r, r+W−1]` 并 `r ← r + W`；只有被
剔除时才 `r ← r + 1`。因此每个窗口只有首行真正受过 Δ 判据检验，窗口内第 2…W 行是
被整体带入的。记录 `01` 第 5 条描述了「顺序扫描 + Δ 判据」，但未点出这一层。

影响两点：一是流水线 B 若改为逐行评价，相对 RSH 的改进空间比原先预估的大；二是与
`07` 第 1 点「全行评价 vs 划分后评价」直接相关，解释该点时应一并说明。

## T12：T1 的主口径与固定简单划分规则（2026-11-04 新增）

两条都是 T1 落笔前必须先定的接口问题，均为规划方本轮提出，不是仓库已有结论。详细论证见
`08` §6。

**（一）「固定简单划分」应方向中性。** T1 把「划分后评价」列为要加的功能，但未规定该固定
划分用什么规则（`06` 与 `candidates.md` 均未见）。建议不用 RSH 的 Δ 判据，只用
`nz_r ≤ τ` 送残余。理由：T6 已判定 NPU 上该送残余的方向可能相反且待实验确定，若第一层
拿一个方向待定的筛子给候选排名次，名次不可用。第一层只承担「删掉短行之后结构还剩多少」
这个问题，Δ 方向整个留给第 2 层 T6。

另须在 T1 写明：已有候选自带分组，对它们而言「划分后评价」要讲清是在**谁的**分组上删行，
否则会与分歧二要求的两套数字（自身组边界 vs 固定 W16）混成四种组合。

**（二）须先定主口径，避免组合爆炸。** 四条扩展正交展开为 4 个 `W` × 2 个视图 × 2 个条件
（全行 / 划分后），再叠分歧二的 2 套（自身组边界 / 固定切窗），每候选 32 组数字；首轮候选
数量下该量级无法用于判断。建议先定一个主口径作为排名依据（候选口径：`W=16` + 对称置换
视图 + 划分后评价），其余维度只对少数代表性候选做敏感性检查。

T12 与 T3 耦合（主口径决定候选排名依据），应同轮决定。

## T9 的修订与 T13（2026-11-04）

**不存在「离线解码 Bitmap」这个选项。** 离线解码即把解码结果落盘，而解一个 16×16 Bitmap
块落盘后就是 512 B 的 `Dense16`——两者是同一操作的两种叫法。Bitmap 载荷的全部价值在于：
「以压缩形式驻留 GM」，离线解码恰好丢掉这个价值。所以只有两个点、不可兼得：压缩驻留 GM
但运行时必须经 AIV 解码并付三趟流量；或稠密驻留 GM 但零解码、AIC 直装。

三趟是结构性成本而非实现未优化：AIV 解完的稠密块在 UB，要让 AIC 吃到必须经 GM——CANN
9.0.0 `dav_c220/kernel_operator_data_copy_impl.h` 中 UB→TSCM 普通拷贝与 ND2NZ 重载都依赖
TPipe/KFC（先写 GM 再发 Scm 消息由 AIC 搬入 L1），NeutronSparse §3 亦写明 910B 这代解耦
设计中「the direct Cube-to-Vector path is removed」。

**故 T9 改为三方对比**：`Bitmap 运行时解码` / `Dense16 + DenseTail 离线预排` /
`Index`（很稀疏块参照）。两点要求：

1. `DenseTail`（kind 3）必须与 `Dense16` 作为一个组合参与比较。它同样零解码、同样可离线
   预排，但只付 `32 × valid_k` B；而 `T = ceil(|U_w|/16)` 必然产生一个不满的尾块，所以
   每个窗口至少有一块可走 DenseTail。只比 `Dense16` 会高估「零解码」一侧的代价。
2. **分开报告 GM 容量与搬运流量**，不要合成单一指标。按 `05` 末节的算术，这两个轴的结论
   可能相反：真实 ρ≈0.15–0.24 折算每块 z≈38–61，此时 Dense16 约为 Bitmap 的 3–4 倍
   （容量轴劣势明显）；但单次搬运中 A 只占约 6%（M=16），多占的流量会被该占比摊薄。

**用户判断（已记录）：** 不看好 Dense-NZ，理由是内存占用过大。`05` 末节的算术支持该判断在
容量轴上成立。若 T9 结论确为 Dense-NZ 在真实 ρ 下落败，其价值仍在于排除「AIC 侧代价只
取决于 T」这一简化假设，使第 1、2 层确认上游目标函数必须带 z。

**T13（前置核对）：** `PROJECT_HANDOFF.md` §2 表中 `Dense16`（kind 0）的「用途」写的是
「无解码对照与分组搬运」，未说明它本身是否已按 NZ 布局预排，而 `05` 用的名字是「NZ 排布的
Dense16」。「E3 现有实现中的 kind 0 是否已按 NZ 预排、抑或仍是 ND 需片上转换」在台账中
没有明确记载。若为后者，`ND2NZ` 开销仍在片上，Dense-NZ 的优势须重算。该核对应在 T9 开跑
前完成，可与 T10 合并。

   去问，且段长–耗时曲线须按 R 分布加权（Cora original 的 p50=48、max=149，右偏明显）。
2. **T9 相关的 Dense16/Bitmap 容量比**：由合成矩阵推出的 3–4 倍改为 Cora 实测的
   **6.5–8 倍**（ρ=0.0613–0.0924，折算 z≈16–24）。Cora 上 Index 全面优于 Bitmap，
   T9 中 Index 不应只当参照。

两组矩阵在这两项幅度上差近一倍，**说明幅度强烈依赖矩阵**，不宜由单张矩阵定常数；T1 重测
后应给跨矩阵分布。
