# 存储层：结构与载荷，Bitmap 与 Dense-NZ

## 用户选 Bitmap 的依据（E3 r7）

覆盖 68 组输入、5 条路径、5 个比较块，共 408 个进程、888420 次调用（调用数用于覆盖和重复测量，不是独立样本）。

16×16 FP16 块，非零数 z，按 32 B 对齐后的载荷：

| z | Bitmap/B | Index/B | Dense16/B |
|---|---|---|---|
| 8 | 64 | 32 | 512 |
| 32 | 96 | 96 | 512 |
| 128 | 288 | 384 | 512 |
| 256 | 544 | 768 | 512 |

- 约 z=32 是 Bitmap 与 Index 的存储交点，但不能直接当运行时路由阈值。
- 61 个非空合成组中，Index 在 33 组更快，Bitmap 在 19 组更快，9 组先后变化。
- 结论：两者各有适用条件；Dense16 直接路径在几何平均观察中仍有低成本优势，应保留为局部回退和对照。

## 讨论结论：类 RS-tile 格式分两部分

1. **结构部分**：窗口偏移 + 每个窗口压缩后的列号（决定 Gather 哪些 B 行）。逻辑 Tile 处在 row window 中，这部分不可少。
2. **载荷部分**：每个 16×16 块里的值怎么存，可以是 Bitmap、Index 或 NZ 排布的 Dense16。

用户确认：**此前强调的 Bitmap 指的是载荷部分。** 选 Dense-NZ 载荷不等于放弃类 RS-tile。

## 为什么 910B 上要单独考虑

- GPU 上解码在同一 SM 的 shared memory/寄存器完成，很便宜，所以 RSH 等论文默认压缩格式。
- 910B 上 AIC 不能解 Bitmap，只能交给 AIV；按 E2 查到的路径，解码后要写回 GM 再由 AIC 读入：读 Bitmap + 写稠密块 + 读稠密块，比直接读预排稠密块流量还多。
- 混合执行时 AIV 还要处理残余路径，解码会与残余工作抢资源。
- 粗算 A 占总供数比例：M=16 时 A 块 512 B 对 B 块（K16×N256 fp16）8 KB，约 6%；W=128 时 8 个 A 块共 4 KB 对 8 KB，约三分之一。小窗口下压缩 A 只能省几个百分点。

## 可行性证据

E0 补测中，预排布 A 从 GM 直装 L0A：直装扩展 4/4、完整集成 17/17、逐次覆盖 120 次全部通过，不经过 AIV。修复时需加 M→MTE2、MTE2→M 同步事件，这部分开销要计入性能实验。**限制：只证明了小尺寸（M16）正确性，没有证明性能。**

## 为什么其他论文没提（推测）

- GPU 论文不存在跨核解码问题。
- NeutronSparse 只写 "We store the AIC-assigned dense core in a BitMap to enable sequential access"（§5.2.2），没给 AIC 侧解码方式，也没和稠密载荷对照。
- 稠密块格式（BCSR、Blocked-ELL）本身不新，单独难算贡献。

研究价值：NPU 解耦架构特有的格式取舍，适合作为有数据支撑的设计决策和消融，大概撑不起独立贡献点。

对上游的影响：载荷为 Dense-NZ 时 A 侧代价只取决于块数 T；为 Bitmap 时还依赖每块 z，上游目标函数要变。最好在第二层定型前有初步结论。

## 2026-11-04 补充：Dense-NZ 的定义与取舍条件（答 `07` 第 5 点）

### Dense-NZ 是什么

名字两半各管一件事，定义出处为本文上节「载荷部分」一条：「可以是 Bitmap、Index 或
**NZ 排布的 Dense16**」。

- **Dense 这一半**：块里存满，不压缩。`PROJECT_HANDOFF.md` §2 编码表中为 `Dense16`、
  `kind = 0`、载荷「256 FP16，512 B」。一个 16×16 fp16 块不论有几个非零都原样存下 256 个
  位置，零也存，字节数恒为 512 B。表中另三种都带压缩或裁剪：`Bitmap16`（kind 1）为 16 个
  u16 位图加非零值，`32 + 2z` B；`LocalIndex16`（kind 2）为 z 个 u8 位置加值，
  `3z + (z mod 2)` B；`DenseTail`（kind 3）为稠密但砍掉尾部全零列，`32 × valid_k` B。
- **NZ 这一半**：按昇腾 Cube 所需的分形布局**离线**排好。NZ 是 L0A/L0B 期望的内部布局，
  `ND2NZ` 是 CANN 中把行主序 ND 转成 NZ 的 DataCopy 接口（`03` 第 11 行）。Dense-NZ 的
  含义是该转换在 host 侧预先做掉，落盘即为 NZ 布局，运行时从 GM 直装 L0A，既不在片上
  转换，也不需要任何解码。

### 它解决的问题与真实卖点

论点见本文「为什么 910B 上要单独考虑」。要点是：Dense-NZ 的卖点**不是省字节**——按字节它
在稀疏块上明显劣势（z=8 时 Bitmap 64 B、Index 32 B，Dense16 为 512 B），只有 z 很大时才
翻盘（z=256 时 Bitmap 544、Index 768，Dense16 仍 512）。它的卖点是**把解码路径整个去掉**。

配合本文已记的 A 占比粗算（M=16 时约 6%）可得一条判断：若压缩 A 最多省约 6%，而解码要付
三趟流量加 AIV 资源竞争，则小窗口下**不压缩反而可能是对的**。这是 Dense-NZ 值得作为正式
选项的核心理由。

### 为什么不存在「离线解码 Bitmap」这个第三选项（用户提问）

**Bitmap 也能离线解码，但一旦离线解了，它就不再是 Bitmap 载荷——它就是 Dense-NZ。**
「离线解码」意为把解码结果落盘；解一个 16×16 Bitmap 块，结果就是 256 个位置都填好的稠密
块，按 NZ 布局存下即为 512 B 的 `Dense16`。两者是同一操作的两种叫法。Bitmap 载荷的全部
价值在于「**以压缩形式驻留 GM**」，离线解码恰好把这个价值丢掉。

因此只有两个点，不可兼得：

1. 压缩驻留 GM，省容量与 GM→片上流量，但运行时必须解码，而解码只能走 AIV 加三趟流量。
2. 稠密驻留 GM，占容量与流量，但零解码，AIC 直接消费。

**三趟为何躲不掉（结构性，非实现未优化）：** AIV 解完的稠密块在 UB 中，要让 AIC 吃到必须
经 GM。出处两条：CANN 9.0.0 `dav_c220/kernel_operator_data_copy_impl.h` 中 UB→TSCM 普通
拷贝与 ND2NZ 重载都依赖 TPipe/KFC，先把 UB 写 GM，再发 Scm 消息由 AIC 搬入 L1；
NeutronSparse §3 亦写明 910B 这代解耦设计中「the direct Cube-to-Vector path is removed」。
**片上没有 AIV→AIC 直达通路**，故「读 Bitmap + 写稠密块 + 读稠密块」是该路径的固有成本。

据此，比较条件应表述为：**零解码省下的三趟，够不够抵掉稠密驻留多占的容量与流量。**

### 真实 ρ 下的字节代价估算（规划方算术，非仓库已有结论）

本文载荷对比表用 z = 8/32/128/256 四点，易给人「z 大了 Dense16 就赢」的印象。但实际 z 落
在哪里，可由 `03` 的 CSV 表「占用率」一列推出。按 `04` 第 11 行定义 `ρ = NNZ/(W·K0·T)`，
即块密度，折算每块平均非零数 `z ≈ ρ × 256`。

**合成矩阵（192×192、12 窗口）：** ρ = original 0.149、rsh 0.239、rabbit/neutron 0.216，
得 z ≈ 38 至 61。z=38 时 Bitmap 为 `32 + 76 = 108` B 对 Dense16 的 512 B，约 4.7 倍；
z=61 时 Bitmap 为 `32 + 122 = 154` B，约 3.3 倍。

**Cora 真实矩阵（2708×2708、10556 nnz、170 窗口，2026-11-04 补交并核验）：**
ρ = original 0.0613、rsh 0.0924、rabbit 0.0772、neutron 0.0770，**比合成矩阵低一半以上**，
折算得 **z ≈ 16 至 24**。代入编码公式：

| 方法 | ρ | z | Bitmap | Index | Dense16 | Dense/Bitmap |
|---|---|---|---|---|---|---|
| original | 0.0613 | ≈15.7 | ≈63 B | ≈47 B | 512 B | **8.1×** |
| rsh | 0.0924 | ≈23.7 | ≈79 B | ≈71 B | 512 B | **6.5×** |
| rabbit | 0.0772 | ≈19.8 | ≈72 B | ≈59 B | 512 B | **7.2×** |
| neutron | 0.0770 | ≈19.7 | ≈71 B | ≈59 B | 512 B | **7.2×** |

即真实矩阵上 z 落在本文表中 z=8 与 z=32 两行之间，**离 z=256 的翻盘点比合成矩阵更远**，
Dense16 要多占 **6.5–8 倍** A 存储，而非合成矩阵推出的 3–4 倍。注意 Cora 上 Index 全面
优于 Bitmap（z 远小于本文记载的 z≈32 存储交点），与「很稀疏候选用 Index」的定位一致。

**限定：** Cora 是**单张矩阵**的先导结果，且 `weighted_alpha = 0.0`（属 T4）；合成与真实
两组 ρ 差一半以上，说明该比值**强烈依赖矩阵**，不宜用任一张矩阵定常数。首轮其余五张矩阵
与 ogbn-arxiv 均未跑，T1 重测后应给出跨矩阵分布。出处见
`讨论记录/2026-11-04/2026-11-04-1130-Cora先导结果核验与数字更正.md`。

**用户判断（已记录）：** 不看好 Dense-NZ，理由是内存占用过大。上述算术支持这一判断在
**容量轴**上成立，且真实矩阵数据比合成矩阵更支持它。

### 两条往回拉的考虑

1. **`DenseTail`（kind 3）此前被低估。** 它同样零解码、同样可离线预排，但不必付满 512 B
   （`32 × valid_k` B）。由于 `T = ceil(|U_w|/16)` 必然产生一个不满的尾块，每个窗口至少有
   一块可走 DenseTail。故「零解码」一侧的真实代价不是 512 B 乘块数，比较时应把
   `Dense16 + DenseTail` 作为一个组合。
2. **容量与流量是两个轴，不要混。** A 多占 6.5–8 倍（Cora）或 3–4 倍（合成）容量是 GM
   足迹问题；而单次搬运中 A 只占
   约 6%（本文 M=16 时 512 B 对 B 的 8 KB），多占的流量乘到端到端会被该占比摊薄。
   「内存太大」在容量轴成立，在流量轴影响小得多。

### 对 T9 的修订建议（规划方建议，非仓库已有结论）

既然不存在「离线解 Bitmap」这一选项，T9 不应写成「Dense-NZ 离线预排 vs AIV 解码 Bitmap」
的两方对比，而应是三方：`Bitmap 运行时解码` / `Dense16 + DenseTail 离线预排` /
`Index`（很稀疏块的参照）。并且须**分开报告 GM 容量与搬运流量**，不要合成单一指标——按
上节算术，这两个轴的结论可能相反。

若 T9 结论为 Dense-NZ 在真实 ρ 下输给 Bitmap，其价值仍在：可据此排除「AIC 侧代价只取决于
T」这一简化假设，使第 1、2 层确认上游目标函数必须带 z。这与本文已有判断一致——该方向
适合作为有数据支撑的设计决策与消融，撑不起独立贡献点。

### 一处台账未写明、须核对的地方（规划方指出）

`PROJECT_HANDOFF.md` §2 表中 `Dense16`（kind 0）的「用途」写的是「无解码对照与分组搬运」，
**未说明它本身是否已按 NZ 布局预排**；而本文用的名字是「NZ 排布的 Dense16」。因此
「E3 现有实现中的 kind 0 是否已按 NZ 预排，抑或仍是 ND、需片上转换」在台账中没有明确记载。
该差别影响不小：若为后者，`ND2NZ` 开销仍在片上，Dense-NZ 的优势须重算。建议并入 T9 的
前置核对，或与 T10 一并查。
