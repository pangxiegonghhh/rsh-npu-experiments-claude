# 存储层：结构与载荷，Bitmap 与 Dense-NZ

## 用户选 Bitmap 的依据（E3 r7）

覆盖 68 组输入、5 条路径、5 个比较块，共 408 个进程、888420 次调用（调用数用于覆盖和重复测量，不是独立样本）。

16×16 FP16 块，非零数 z，按 32 B 对齐后的载荷：

| z | Bitmap/B | Index/B | Dense16/B |
|---|---|---|---|
| 8 | 64 | 32 | 512 |
| 32 | 96 | 96 | 512 |
| 128 | 288 | 384 | 512 |
| 256 | 544 | 768 | 512 |

- 约 z=32 是 Bitmap 与 Index 的存储交点，但不能直接当运行时路由阈值。
- 61 个非空合成组中，Index 在 33 组更快，Bitmap 在 19 组更快，9 组先后变化。
- 结论：两者各有适用条件；Dense16 直接路径在几何平均观察中仍有低成本优势，应保留为局部回退和对照。

## 讨论结论：类 RS-tile 格式分两部分

1. **结构部分**：窗口偏移 + 每个窗口压缩后的列号（决定 Gather 哪些 B 行）。逻辑 Tile 处在 row window 中，这部分不可少。
2. **载荷部分**：每个 16×16 块里的值怎么存，可以是 Bitmap、Index 或 NZ 排布的 Dense16。

用户确认：**此前强调的 Bitmap 指的是载荷部分。** 选 Dense-NZ 载荷不等于放弃类 RS-tile。

## 为什么 910B 上要单独考虑

- GPU 上解码在同一 SM 的 shared memory/寄存器完成，很便宜，所以 RSH 等论文默认压缩格式。
- 910B 上 AIC 不能解 Bitmap，只能交给 AIV；按 E2 查到的路径，解码后要写回 GM 再由 AIC 读入：读 Bitmap + 写稠密块 + 读稠密块，比直接读预排稠密块流量还多。
- 混合执行时 AIV 还要处理残余路径，解码会与残余工作抢资源。
- 粗算 A 占总供数比例：M=16 时 A 块 512 B 对 B 块（K16×N256 fp16）8 KB，约 6%；W=128 时 8 个 A 块共 4 KB 对 8 KB，约三分之一。小窗口下压缩 A 只能省几个百分点。

## 可行性证据

E0 补测中，预排布 A 从 GM 直装 L0A：直装扩展 4/4、完整集成 17/17、逐次覆盖 120 次全部通过，不经过 AIV。修复时需加 M→MTE2、MTE2→M 同步事件，这部分开销要计入性能实验。**限制：只证明了小尺寸（M16）正确性，没有证明性能。**

## 为什么其他论文没提（推测）

- GPU 论文不存在跨核解码问题。
- NeutronSparse 只写 "We store the AIC-assigned dense core in a BitMap to enable sequential access"（§5.2.2），没给 AIC 侧解码方式，也没和稠密载荷对照。
- 稠密块格式（BCSR、Blocked-ELL）本身不新，单独难算贡献。

研究价值：NPU 解耦架构特有的格式取舍，适合作为有数据支撑的设计决策和消融，大概撑不起独立贡献点。

对上游的影响：载荷为 Dense-NZ 时 A 侧代价只取决于块数 T；为 Bitmap 时还依赖每块 z，上游目标函数要变。最好在第二层定型前有初步结论。
