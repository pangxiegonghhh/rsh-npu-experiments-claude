## 1. 规则（执行方从原代码提取，并对四份实测 commands.bin 逐记录重放一致）

1. 每个窗口按 16 行一块（tile）切开。**段片不跨 tile、不跨窗口**。
2. 每个 tile 内先切成最大连续段片；补零行单独成一类，和真实 B 行不混在一组。
3. 从左往右贪心：下一片和当前片**等高、源起点等步长、目的槽连续、同一类（真实 / 补零）、`步长×N ≤ 65535`**，就并入同一次调用；遇到第一片不符就结束，不回溯。
4. 设备端每条记录 `[row,h,s,stride,…]` 对应一次 DataCopy：`ndNum=s, nValue=h, srcNdMatrixStride=stride×N, srcDValue=N`。
5. `srcNdMatrixStride` 是 uint16，单位是元素（CANN9 文档）。N128 时源起点距最多 511 行，N256 最多 255 行。

## 2. 关键数

| 顺序 | N | 实测调用 | 固定段片最优 | 允许段片细分最优 | 不设 stride 上限 |
|---|---:|---:|---:|---:|---:|
| B0 | 128 | 4,947 | 4,947 | 4,830 | 4,944 |
| B0 | 256 | 4,969 | 4,969 | 4,863 | — |
| B1 | 128 | 2,481 | 2,481 | 2,379（−4.1%） | 2,442 |
| B1 | 256 | 2,521 | 2,521 | 2,430 | — |

- Cora B1/N128 的 2,481 次调用中，**1,729 次（70%）是单段（ndNum=1）**，752 次是合并调用。
- 约 87 ns/调用是「完整回放时间 ÷ 调用数」的流水摊销值，含命令读取、标量循环、转置加载、消费与同步；不是单次 DataCopy 的延迟。
- 合并调用与单段调用是否同价：**从未分开测过，未知**。

## 3. 规划方判读

1. **合并算法本身的提升空间很小**：贪心在「不细分段片」下已是最优；允许细分也只少 4.1%。真正的抓手只能是置换，不是描述符优化。
2. **更正**：ND 路径的补零行也要发调用，每个有补齐的 tile 一次（每个窗口至多一次）。补齐行不按行计价，但会多一次调用。
3. **b 是混合平均值**：70% 单段 + 30% 合并调用。若两者单价不同，分界 4.6 只在「调用构成和 Cora B1 相近」时成立。
4. **N 越大，stride 上限越紧**：N128 时只差 1.6%；N512 时源起点距只能到 127 行。
5. **预处理可缓存**，但调用清单依赖行序、N、tile 切法和规则，不只依赖 A。
