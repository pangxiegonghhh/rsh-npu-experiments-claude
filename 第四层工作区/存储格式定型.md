# 第四层定型：AIC 部分采用稠密 W×1 列块（2026-11-12）

**决定（用户 2026-11-12 拍板，选项 A）：** AIC 窗口的载荷直接存成**稠密 W×1 列块**（W=16），零也存。格式与 Ascend-SpMM 的 W×1 BSR、AscSpMM 的 Vector-CSR Adata 相同。原计划的 Bitmap / Index 载荷不再研究。第 4 层不再作为研究点，它带来的约束写进第 2 层（成窗）和第 5 层（数据准备）。

出处：`讨论记录/2026-11-12/2026-11-12-0640-任务3调研与第四批拍板-小包二十八.md`。

## 1. 格式

对每个 AIC 窗口（新编号下连续的 16 行）存三部分：

- **列号表：** 窗口的列并集 U_w，按升序排列，用来取 B 的行；
- **载荷：** 每个列号对应一个 16 元素向量，内容是这 16 行在该列上的值，没有非零的位置填 0；
- **补齐：** 列块数补零到 16 的倍数，凑成整的 16×16 块。

这些向量在 GM 里连续存放，g 个块（Ascend-SpMM 取 g=6）用一次 DataCopy 搬入 L1。

玩具例子：一个窗口用到列 {3, 7, 9}，就存 3 个 16 元素向量，再补 13 个零向量凑成一个 16×16 块，列号表为 [3, 7, 9]。

## 2. 依据

1. **两篇论文的 AIC 都直接消费这种格式，不需要解码。**
   - Ascend-SpMM §3.4 ★：W×1 块可以拼成 W×(g·k) 的 tile，减少 A 的 MTE2 指令数；
   - AscSpMM §IV-B ★：Adata 作为规则操作数直接交给 AIC。
   - 用户读代码确认的链路是 GM→L1 用 DataCopy，L1→L0A 用 LoadDataWithTranspose，再 Mmad。
2. **NPU 上没有 GPU 那样的线程可以顺手解码。** Bitmap / Index 载荷只能交给 Scalar 或 AIV 去解码，会拖慢给 Cube 供数。AscSpMM §II-B ★ 明确指出，逐个下标的 Scalar 处理跟不上 Cube 的供数需求。RS-tile 的 Bitmap 是为 GPU 设计的。
3. **省带宽的空间很小【推】。** 一个列块的 A 是 16 个 FP16，即 32 字节；对应要取的 B 行是 N×2 字节，N=128 时为 256 字节。A 的零就算全存，也只占 B 流量的约 1/8，压缩 A 却要付出解码代价。
   - 注意，cora 上 Cube 的 MAC 有 89.1% 花在零上（T24），这是算力浪费，不是带宽浪费；
   - T24 已证明它与列数成正比，只相当于放大 α。

## 3. 对其他层的约束（详见 `第二层工作区/第二层设计约束.md` §2）

1. AIC 的行凑满 16 行一个窗口；
2. 每个窗口的列块数按 16 取整，判据同时看 ΔT 与 ΔU；
3. 输出行在新编号下连续；
4. 第 5 层：A 直装，不做解码。原流程图第 5 层「A 直装或解码」中的「解码」分支取消。
