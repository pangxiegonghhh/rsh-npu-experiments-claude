# RSH-SpMM 向 Ascend 910B 迁移研究：完整项目交接材料

> 整理日期：2026-10-20  
> 用途：提供给其他 agent 阅读、评估和继续讨论。  
> 当前阶段：已完成基础迁移实验及 D0–D3 诊断，正在讨论 NPU 执行设计路线。  
> 本材料包含实验背景、方法、主要数据、结论边界和后续计划，不包含全部逐次原始计时样本。  
> **本材料属于研究背景交接，不代表授权接收方自动启动设备、修改内核或继续旧实验计划。**

---

## 1. 项目目标与用户真正希望开展的研究

用户原本的设想是：

1. RSH-SpMM 是针对 GPU 的方法，具有细粒度行划分、结构重排和混合执行机制。
2. Ascend NPU 与 GPU 的计算单元、存储层级、数据布局、同步和流水方式不同。
3. 先实现一个基础迁移版本，判断 RSH 的结构利用思想在 NPU 上是否有性能潜力。
4. 如果看到足够明确的收益，再针对 NPU 重新设计操作数布局、数据搬运、流水、数据复用和输出过程。
5. 论文贡献可以来自必要且有效的 NPU 执行机制，不要求首先发明新排序或新分流算法。

用户特别关注 RSH 中的 GPU 执行细节，例如：

- MMA 操作数的线程—寄存器映射。
- B 的加载与寄存器片段组织。
- A 的解码与操作数构造。
- 双缓冲、预取与计算重叠。
- 输出片段的向量化写回。

用户希望弄清楚：这些设计迁移到 910B 后，对应的研究问题是什么，各模块之间如何连接，应按什么顺序开展研究。

**当前不能把项目目标擅自改成“必须先提出新的联合分组与分流算法”。可以保留 RSH 的结构选择方法，把创新放在 NPU 执行层。**

## 3. 当前最重要的研究判断

现有证据支持：

> RSH 式结构利用在当前 Ascend 910B 原型上具有局部、可重复的常驻调用收益，足以支持一次有针对性的 NPU 执行设计尝试。

现有证据尚不支持：

- 所有矩阵都能加速。
- 已经达到 RSH 在 GPU 上的效果。
- 已经优于完整 NeutronSparse 或成熟稀疏库。
- 已经证明完整应用端到端收益。
- 已经提出并验证了新的划分算法。
- 已经完成论文新颖性证明。
- 当前代码存在可优化之处，所以优化后必然有更大收益。

最直接的 D3 结果：

- J 相对简化长度优先流程 L，综合时间比 `L/J = 1.108032`。
- thermal1/N64：`L/J = 1.630418`。
- web-NotreDame/N64：`L/J = 1.378387`。
- cit-HepTh/N256：`L/J = 0.814833`，即 J 约慢 22.7%。

因此，需要同时保留三个认识：

1. 部分结构上的收益已经比较明显。
2. 综合收益有限，但在本轮受控条件下可以重复。
3. 存在明确退化，不能只报正例。

## 4. 术语与符号

| 符号 | 含义 |
|---|---|
| A | 稀疏矩阵，形状为 M×K |
| B | 稠密矩阵，形状为 K×N |
| Y | 输出矩阵，Y=AB |
| W | 行窗口高度，当前固定为16 |
| N | B 的特征宽度，实验主要采用16、64、256 |
| K16 | 沿压紧列方向划分的16列计算块，不是16行窗口 |
| G | 交给 Cube 的完整窗口 |
| S | 被划分规则移出的非尾残余行，交给 AIV |
| T | 动态扫描结束后不足 W 行的尾部，当前主要交给 AIV |
| Z | 单独记录的零行集合；具体零行处理策略随历史阶段而异 |
| R | H-Skip 保留计算的原始行集合，即原始行全集去掉 T |
| C(r) | 为行 r 生成的相似行候选集合，主要用于重排 |

需要特别区分：

- W、N、K16 属于不同维度。
- 行重排不改变矩阵全局 NNZ 或全局稀疏度。
- 重排会改变组内列并集、局部填充、计算块数量和访问顺序。
- 当前 G 与 S/T 的输出行归属互斥，没有把同一原始行的非零跨两条路径拆开后累加。
- 当前不做超长行拆分。

## 5. 文献认识与创新边界

本节主要沿用截至 2026-10-16 已有的定向核查，不代表截至当前完成了全部相关工作的穷尽检索。

### 5.1 RSH-SpMM

论文：

**RSH-SpMM: A Row-Structured Hybrid Kernel for Sparse Matrix-Matrix Multiplication on GPUs**

原文：

https://arxiv.org/html/2603.08734v1

主要组成：

- Locality-aware reordering。
- 窗口相关的细粒度行划分。
- RS-Tile 表示。
- Tensor Core 与 CUDA 两条执行路径。
- GPU 操作数构造、寄存器片段映射、预取和双缓冲。
- 负载均衡。

当前项目借鉴的是它的结构组织与划分思想。

当前原型包含移植补齐，并不是作者 GPU 实现的逐项完整复现。阈值、候选截断、断连处理和尾窗策略不能全部冒称为作者原始实现。

### 5.2 NeutronSparse

论文：

**NeutronSparse: Coordinating Heterogeneous Engines for Sparse Matrix Multiplication on NPUs**

原文：

https://arxiv.org/html/2606.22482v1

已有核查确认，它不只是“将矩阵简单分成稠密和稀疏两块”：

- 初始阶段有稀疏行抽取。
- 对剩余子矩阵还有稀疏列抽取。
- 同一原始行可能同时产生 AIC 和 AIV 工作。
- 已有硬件校准的分工依据。
- 已有运行反馈和双向工作迁移。
- 已有全局与局部重排。
- 已有 B 局部性、缓存和 tile 选择设计。
- 已有 AIC/AIV 双缓冲。

因此，不能直接把下面这些宽泛表述作为本项目的新颖性：

- 首次 AIC/AIV 协同。
- 首次 NPU 上结构重排。
- 首次 B 复用。
- 首次双缓冲。
- 首次自适应分工。

公开 **NeutronSparseLite** 也不能未经核对就视为完整论文手写内核：

https://github.com/iDC-NEU/NeutronSparseLite

已有核查发现，公开 Lite 实现与论文描述在预处理、框架调用、数值与执行细节上存在需要进一步对齐的地方。目前没有在本项目中完成其公平性能复现。

另外，**NeutronSparse 与 NeutronAscend 是不同论文**，不要混用名称或机制。

### 5.3 GROOT

已有核查认为：

- 可以作为替代重排方法或对照。
- 不应按论文年份判断一定优于或弱于 RSH。
- RSH 自己也有接近的 kNN、树结构和遍历排序流程。
- 替换排序后会同时影响后续成窗和分流，不能把两部分收益简单相加。
- GROOT 尚未接入本项目做性能实验。

### 5.4 当前创新定位

项目可以沿用 RSH 的划分，把贡献放在执行层。

更有说服力的贡献形式是：

> 发现细粒度结构选择在 910B 执行时引入了某种具体代价，提出对应的布局、执行批次、复用或调度机制，并证明其完整性能收益、适用范围及相对已有工作的差异。

普通双缓冲、替换接口、正确使用 L1/L0 等，首先属于建立可信实现所需的基础工作。具体机制是否足够新颖，需要针对最终设计再核查。

## 6. 当前结构流程与划分规则

### 6.1 重排

当前 RSH-style 重排主要采用：

1. 根据共享列生成候选集合 C(r)。
2. 低频列优先。
3. 候选预算256。
4. 加权 Jaccard 相似性。
5. kNN 的 k=16。
6. 构造无向邻接关系。
7. 最小生成森林。
8. 确定性 DFS。
9. 固定行窗内一轮局部2-opt调整。
10. 孤立行置末尾。

这是有候选截断和确定性采样的近似搜索，不是精确全局近邻。

### 6.2 窗口相关划分

设当前候选窗口为：

```text
[r0, r1, ..., r15]
```

令每行的非零列集合为 `support(r)`。

当前实现计算：

```text
others = support(r1) ∪ ... ∪ support(r15)

Delta = |support(r0) - others|
```

如果：

```text
Delta < tau_inc
且
nnz(r0) <= tau_nnz
```

则：

```text
将首行 r0 放入残余集合 S；
扫描位置向后移动1行；
重新判断下一候选窗口。
```

否则：

```text
接受整个16行窗口；
放入 G；
扫描位置向后移动16行。
```

不足16行时进入 T。

**应保持上述条件方向，不能按直觉把移出条件反过来。**

当前所谓“窗口参与分流”，主要就是这个 RSH 式规则：

- 首行去向与当前窗口关系有关。
- 移出首行会改变下一次窗口成员。
- 因此路径选择和成窗相互影响。

C(r) 用于前面的重排。划分时并没有每次重新从 C(r) 中任意选择16行。

### 6.3 零行策略的历史差异

早期 H-V 使用扫描过程中处理零首行的方式，窗口内部可能保留零行。

D3 的 L/F/J/O 则统一在成窗前移除全部零行，零输出仍完整保留。

因此，D3 的 J 与历史 H-V 不是所有策略都完全相同。D3 增加 J0 等控制，帮助区分这种变化。

## 7. 平台、输入与性能口径

### 7.1 平台

实测平台：

- Ascend 910B2。
- 64 GB 设备内存。
- 后期会话使用 CANN9.0.0。
- 主要运行配置为24个 AIC、48个 AIV。
- 不同租用会话的物理卡号和容器可能变化。

不能把不同会话的绝对时间直接拼接。

具体搬运路径和接口支持应以当前芯片与本地 CANN 为准，不能套用其他硬件代际的能力。

### 7.2 输入

八张矩阵：

1. Boeing_bcsstk38
2. FEMLAB_ns3Da
3. HB_bcsstk17
4. SNAP_ca-HepTh
5. SNAP_cit-HepTh
6. SNAP_email-Enron
7. SNAP_web-NotreDame
8. Schmid_thermal1

主要宽度：

```text
N ∈ {16, 64, 256}
```

因此六主版本和 D3 的完整配置集合为：

```text
8矩阵 × 3宽度 = 24配置
```

使用真实矩阵稀疏结构及已保存、可复现的带符号 FP16 数值，不能默认等同原始应用中的所有数值。

### 7.3 精度与正确性

- A/B 输入 FP16。
- 累加 FP32。
- 输出 FP32。
- CPU 参考由相同存储输入提升到 FP64 计算。
- 初始统一容差为 `atol=1e-2、rtol=1e-2`，各轮具体以冻结协议为准。
- 不为某一方法单独放宽容差。
- 检查完整真实输出、零行及相关 padding。
- 使用 B 和 -B 等变化验证，避免跨调用误用旧 B。

不是每一次正式计时都将输出拷回 CPU；数值检查覆盖方式见各轮协议，不能把已有检查夸大为“每次采样都完整拷回验证”。

### 7.4 计时边界

主要指标是：

> 输入已经驻留设备时的一次同步完整调用耗时。

包含：

- 必要输出清零。
- 必要中间缓冲清零。
- 调用内 B 行收集。
- 计算。
- 输出恢复。
- 同步。

不完整包含：

- CPU 重排。
- CPU 分流。
- 格式构建。
- 首次计划和输入上传。
- 实际应用中每轮 B 的主机到设备更新。

CPU 组件、`device_prepare_us`、`first_us` 和稳态时间分别记录，不能直接拼成完整应用端到端结果。

### 7.5 统计约定

时间比：

```text
时间(A) / 时间(B)
```

大于1表示 B 更快。

例如：

```text
1.20×加速 ≠ 耗时减少20%
1.20×加速对应耗时减少约16.7%
```

早期每点三独立进程，每方法十次预热、三十次采样。

后期增加至每点十独立进程，方法随机交错，并采用同实现的不同分配副本作空对照或方向复核。

注意：

- 30次进程内迭代不是30个独立实验。
- 同一矩阵的三个 N 不是三张独立矩阵。
- 各阶段速度比不能直接连乘。
- 不同阶段绝对延迟不能直接配对。
- 后期的条件区间不代表未知矩阵总体。
- 空对照保护值不是普遍适用的显著性阈值。
- 全部八矩阵均已被使用，不能再称为未见测试集。

## 8. 第一轮：六个主版本

### 8.1 设计

| 版本 | 结构与执行方式 | 尾部处理 | 输出范围 |
|---|---|---|---|
| V0 | 原始行，全 AIV CSR | AIV | 完整 |
| V1 | 原始行序、固定 W 行窗、列压紧、全 Cube | 补零走 Cube | 完整 |
| V2 | RSH-style 重排后固定行窗、全 Cube | 补零走 Cube | 完整 |
| H-V | 重排及窗口相关划分，G走Cube、S走AIV | T走AIV | 完整 |
| H-C | 与H-V相同G/S/T | T补零走Cube | 完整 |
| H-Skip | 与H-V相同G/S/T | 不执行T | 部分输出 |

H-V/H-C/H-Skip 之间冻结行序和 G/S/T，只改变 T 的执行方式。

H-Skip 仍执行 S，不是只测 Cube。

H-Skip 补充：

- V0-R：只计算相同保留行集合 R。
- V2-R：将已有排列限制到 R 后，按其固定窗口方式构造布局。
- 不重新运行重排。
- R 通常不是连续前缀。

### 8.2 综合结果

下表每一行来自其自身阶段内配对，不能连乘。

| 比较 | 24点几何平均 |
|---|---:|
| V0/V1 | 1.177924 |
| V1/V2 | 1.074431 |
| V2/H-V | 1.081573 |
| V0/H-V | 1.356550 |
| H-V/H-C | 0.999228 |
| V2-R/H-Skip | 1.071785 |
| H-V/H-Skip | 0.995682 |

前五项是完整输出比较。

`V2-R/H-Skip` 是相同保留行 R 的部分输出比较。

`H-V/H-Skip` 的输出范围不同，只能用于尾窗诊断。

### 8.3 重要观察

**重排收益集中。**

V1→V2 综合约1.074431，但事后去掉 ns3Da 的三个点，其余21点约1.006422。

这只是组成敏感性分析，不是删除 ns3Da 后重新定义主结果。

ns3Da 的块数约从88895降到17621，减少约80.18%，说明某些结构确实能被重排显著改善。

**宽 N 下优势不足。**

H-V 相对 V0 的宽度分组时间比：

| N | V0/H-V |
|---:|---:|
| 16 | 1.933796 |
| 64 | 1.330084 |
| 256 | 0.970549 |

因此不能只看全24点平均值。

**尾窗不是当前优先矛盾。**

- H-V/H-C 接近1。
- H-V/H-Skip 接近1。
- 八矩阵尾窗均不超过15行。
- 尾窗 NNZ 占比最高约0.13166%。

H-Skip 不是严格数学上界，因为仍有公共开销，而且删除尾部可能改变调度和缓存。

**当时归因仍不清楚。**

V2→H-V 同时改变：

- 组成员。
- 路由。
- 零行处理。
- 窗口数量。
- 中间输出大小。
- 混合执行。

不能把全部收益直接称为“结构分流贡献”。

## 9. 为什么 H-Skip 后设计 D0–D3

当时存在四个未解决的问题：

1. 小幅收益能否与测量波动区分？
2. 收益究竟来自结构利用，还是空窗口、初始化和输出处理？
3. 默认4/2是否不适合当前后端？
4. 六版本缺少长度优先混合对照，尚未直接回答结构何时参与分流的问题。

因此计划：

```text
D0：先确认测量能分辨收益
  ↓
D1：查收益来源和主要成本
  ↓
D1b：修正D1发现的公共清零问题
  ↓
D2：在固定公共后端下确认阈值
  ↓
D3：比较长度优先与窗口相关划分
```

D1b 是根据 D1 结果插入的独立阶段。

D0–D2 主要减少干扰，D3 才直接比较决策流程。

## 10. D0：计时可分辨性

### 10.1 设计

五个代表点：

- ns3Da/N16。
- email-Enron/N64。
- ca-HepTh/N256。
- web-NotreDame/N16。
- thermal1/N64。

比较 V0、V2、H-V，以及同一 H-V 实现的第二标签。

每点十独立进程，每方法十次预热、三十次采样，随机交错。

## 14. D3：长度优先与窗口相关流程比较

### 14.1 三个主流程

| 流程 | 定义 |
|---|---|
| L | 先按长度选 S，再只在 Cube 候选行中做结构重排与成窗 |
| F | 先全局重排，再按与 L 相同的长度规则选同一 S，余行保序成窗 |
| J | 使用同一全局排列，按 RSH 式窗口相关规则移出行或接受窗口 |

L/F 的 S 严格相同：

```text
S = {原始行 r | 0 < nnz(r) <= 8}
```

L/F 的 S 执行次序均为原始行号升序。

共同条件：

- 同一公共执行后端。
- 8/4。
- W16。
- 候选预算256。
- kNN16。
- 两次必要清零。
- 原始 M 完整输出。
- 成窗前移除全部零行。
- 不足16行的尾窗交给 AIV。

### 14.2 主比较回答什么

- L/F：仅将结构组织放到长度分流之前，是否有可靠收益？
- F/J：在全局排列相同条件下，让窗口影响选行和成窗，是否有收益？
- L/J：当前窗口相关流程相对简化长度优先流程表现如何？

限制：

- L/F 还改变重排候选域、权重、采样局部行号和尾成员。
- F/J 还改变路由、组成员、S次序和尾部。

- L 不是完整 NeutronSparse 复现。

## 17. 当前 NPU 实现做到哪里

### 17.1 已确认的代码事实

**A 的表示：**

- A 在预处理阶段被展开成显式补零的16×16块。
- 当前没有完整复制 RSH 的位图解码到寄存器的内核路径。
- 不能认为 A 格式已经最优。

**B 的供给：**

每个 K16 块：

1. 读取16个列引用。
2. 按引用发出16次 B 行 DataCopy。
3. 形成相应片上布局。
4. LoadData 到 Cube 操作数缓冲。
5. 执行 Mmad。

**缓冲与流水：**

- 分配了两份 A/B 缓冲。
- 没有显式组织下一块提前准备的完整软件流程。
- 每次 Mmad 后有 `PIPE_M` 同步。

不能因此断言完全没有硬件重叠。源码只说明值得诊断，不证明这是主要瓶颈。

**输出：**

```text
Cube结果
  → packed GM
  → 独立恢复内核读取到UB
  → 按原始行号写回最终输出
```

存在额外 GM 读写和恢复调用。

**调度：**

- 窗口按核轮转。
- 相邻窗口通常分配到不同核。
- 尚无基于共享列关系的同核片上复用计划。

**AIV：**

- 逐非零收集 B。
- 存在较多串行操作与同步。
- 当前 V0 是较弱的受控机制基线。
- 必须防止将弱 AIV 带来的相对优势误认为结构方法的固有优势。

### 17.2 与 GPU 寄存器映射的对应关系

| GPU侧问题 | 910B侧对应问题 |
|---|---|
| 哪个线程持有哪些寄存器片段 | 操作数以什么布局进入L0A/L0B |
| B怎样直接构成MMA片段 | 不连续B行怎样收集并形成合法Cube输入 |
| 当前计算与下次加载重叠 | 搬运、缓冲、Cube之间如何安排依赖与预取 |
| C寄存器片段连续写回 | L0C写回与原始行映射如何组织 |

不能简单找一个“NPU寄存器”替换 GPU 寄存器。

也不能绝对断言所有数据都必须经过某一固定存储路径。接口合法性、布局与产品支持必须按910B和当前CANN核实。

## 18. 当前整体设计路线

### 18.1 功能链

```text
A结构分析与重排
  ↓
RSH式划分
  ├─ G：准备A/B操作数 → Cube计算 → 输出恢复
  └─ S/T：AIV稀疏计算
  ↓
完整结果Y
```

### 18.2 研究链

```text
已有基础迁移和局部收益证据
  ↓
固定J窗口，定位真实成本
  ├─ 若供数值得处理：
  │    操作数布局＋供数流水原型
  └─ 若其他成本更突出：
       输出恢复、AIV或调度分支
  ↓
完整调用与公平后端比较
  ├─ 无稳定收益：回查假说和新增代价
  └─ 有收益：按剩余问题选择扩展
  ↓
适用范围、完整应用成本、相关工作差异
```

公平基线、准备成本记录和相关工作核查同步推进。

不需要等待全部外部复现完成后才允许做一个小原型，也不能把这些核查全部拖到最后。

### 18.3 各模块关系

| 模块 | 研究问题 | 进入条件 |
|---|---|---|
| 操作数布局 | A/B怎样以Cube可消费布局准备好 | 当前先限制变量，重点诊断B |
| 窗口内流水 | 算当前块时，下一块能否提前准备 | 供数等待有值得处理的成本 |
| 跨窗口复用 | 不同窗口能否共享已准备B片段 | 有足够重复访问，且缓存之外仍有成本 |
| 输出组织 | packed与恢复能否更便宜 | 恢复成本突出，可提前成为主线 |
| AIC/AIV调度 | 是否存在慢端、争用、负载不均 | 有实际时间线或负载证据 |
| 成本感知分流 | 哪些窗口在当前后端值得走Cube | 固定规则持续失配时再进入 |
| 应用验证 | 准备与B更新是否抵消收益 | 开始就记账，集成后完整验证 |

布局与流水互相约束：

- 布局决定每块占多少空间、需要几次搬运。
- 流水决定需要几份缓冲、预取多远、何时可复用空间。

跨窗复用、输出、调度、新分流都是候选分支，不是必须全部实现的清单。

## 19. 最近主线：让细粒度窗口高效供给 Cube

### 19.1 任务定义

在固定 J 的窗口成员、G/S/T 和计算语义下，使 A/B 操作数以更低代价供给 Cube，并验证完整调用是否变快。

固定逻辑窗口，不意味着固定物理执行批次。

可以保留同样的16行窗口，研究：

- 多个K16块成批准备。
- N方向分块。
- 下一块预取。
- 缓冲生命周期与依赖安排。

这不等同于重新设计分流，也不是超长行跨路径拆分。

### 19.2 第一步：离线工作特征统计

统计：

- 每窗口K16块数。
- 各N下的B工作集。
- A填充放大。
- B引用序列。
- 候选搬运批次大小。
- 窗口间重复列引用。
- 输出数量。

B索引重复只是机会指标，不等于已测得重复HBM读取；缓存可能已经吸收部分重复。

### 19.3 第二步：小范围诊断

建议起点：

- thermal。
- web。
- cit。
- ns3Da控制。

覆盖已有N，解释正例、负例与布局恒等控制。

先观察真实混合调用，再通过独立分支、时间线或微基准解释。

可以增加“B已经按需要组织好”的条件诊断，但：

- 改变了存储和缓存条件。
- 不是严格性能上界。
- 不计准备时，不能作为实际方法加速。
- 不可用独立分支时间简单推导真实并发。

如果工具无法隔离某项成本，应报告证据限制，不能编造瓶颈占比。

### 19.4 第三步：只实现一项机制

| 若发现 | 第一项原型候选 |
|---|---|
| 小块搬运和发指令过于细碎 | 多个K16块成批准备 |
| 供算衔接存在等待 | 下一块预取与缓冲轮换 |
| 某些N布局或容量利用差 | N方向分块和操作数布局 |
| 跨窗重复访问值得处理 | 后续研究同核调度与有限驻留 |

初期优先研究窗口内供数。

如果让 AIV 帮助打包，还需计入：

- GM中转。
- 核间同步。
- AIV残余计算与打包的资源竞争。

不能假设910B具有其他代际的直接共享路径。

### 19.5 第四步：完整调用验收

既看机制，也看总时间：

- 是否减少等待或准备？
- 是否引入更多打包、同步和输出成本？
- 完整调用是否超过同层测量波动而稳定改善？
- B变化后是否正确？
- 零行、尾窗、非对齐N、小分支和空分支是否正确？

不能只凭：

- 搬运指令少。
- Cube更忙。
- 子核更快。
- 块数更少。

就判定原型成功。

### 19.6 第五步：公平交叉对照

最小核心：

|  | 当前执行后端 | 新执行后端 |
|---|---|---|
| 长度优先L | 已有对照 | 同样采用新后端 |
| RSH式J | 当前移植 | 新完整方案 |

适用时也给F相同后端，并保留整矩阵AIV对照。

先固定划分参数；若后端改变后发现规则失配，再作为独立阶段校准。

可能结果：

- L/J都相近地变快：说明公共后端改进有用，尚未证明细粒度专用机制。
- J在多个结构上特别获益：继续分析机制与适用范围。
- 新增准备抵消收益：修正或放弃该机制。
- 强AIV消除混合优势：重新限定价值或停止当前假说。
- 前端改善后恢复成为主要成本：转向输出分支。

## 21. 哪些结论可以说，哪些不能说

### 可以说

- 当前原型验证了RSH式结构利用在910B上的局部潜力。
- 当前尾窗处理不是主要优先问题。
- 旧清零路径显著影响过框架比较。
- 8/4通过本轮配置选择规则。
- 仅提前重排未显示可靠综合收益。
- 窗口相关划分相对简化长度优先对照出现了可重复综合信号。
- 有理由开展一次固定窗口的NPU执行诊断与最小原型。

### 不能说

- 已证明普适加速。
- 已完整复现RSH全部GPU优化。
- L就是NeutronSparse。
- J是本项目新提出的算法。
- 已优于完整Neutron或成熟稀疏库。
- 原生清零的10倍改善就是结构算法收益。
- B搬运已经被证明是主瓶颈。
- 索引重复就意味着可节省相同数量的HBM流量。
- 分配两份缓冲就已经实现高效流水。
- 优化后必然更快。
- 已有完整应用端到端收益或可靠复用盈亏平衡次数。
- 当前八矩阵属于未见测试集。
- 普通双缓冲、B复用、AIC/AIV协同本身就是新颖贡献。
