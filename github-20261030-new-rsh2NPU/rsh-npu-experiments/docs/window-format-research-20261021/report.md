# 固定细粒度窗口如何高效供给 Cube：格式研究与设计

日期：2026-10-21。对象：Ascend 910B / Atlas A2，目标软件环境 CANN 9.0.0。

## 1. 结论与接下来的路线

**有值得借鉴的窗口格式，但目前没有证据支持直接选 bitmap 为最终方案。建议先以“W16 窗口目录＋共享原列映射＋可替换 A 编码”为统一接口，优先实现稠密分形分组供给和尾列紧凑存储，再与片上展开的 bitmap、uint8 局部索引做同条件比较。**

这保持用户给定的前提：A 的行重排、窗口成员、AIC/Residual 归属都已确定。格式可以改变同一窗口的数据组织，不能靠重新分流或改变窗口高度获得这轮实验的收益。

路线为：

```text
确认 FP16 Cube 输入契约
    ↓
固定窗口目录、原列映射、正确性不变量
    ↓
稠密分形 / 紧凑尾块 / 位图 / 局部索引：共享同一输入
    ↓
A 装载或展开 + 按映射准备当前调用的 B
    ↓
L1 分组、L0 装载、K16 或多 K16 消费
    ↓
用设备供给耗时和完整调用耗时选型
```

详细证据分为 [GPU 格式比较](gpu-window-formats.md)、[NPU 相关工作](npu-window-formats.md)、[Cube 输入契约](cube-input-contract.md)。论文提供设计依据；下文协议和成本公式是本项目的设计与推导，不冒称论文原格式或已实现的 NPU 性能结果。

## 2. 三个尺度与列映射

| 尺度 | 本项目含义 | 是否与存储包大小相等 |
|---|---|---|
| W=16 | 已定窗口内的16行，M方向 | 固定 |
| K16 | 紧凑列空间的16个槽，归约方向 | 一个包可包含q个K16 |
| N_t | 当前处理的B特征列数 | 运行时选择；物理宽度Np向16取整 |

对窗口 g，设原行号 `rows_g[r]`，有序原列集合 `cols_g[j]`，大小 U_g。它的第 t 个 K16 满足：

```text
A_t[r,k] = A[rows_g[r], cols_g[16*t+k]]       （16*t+k < U_g）
B_t[k,n] = B[cols_g[16*t+k], n_begin+n]       （同一条件）
其余 K 槽：A_t、B_t 均为零
C_g += A_t × B_t
```

这里原 A 的列号就是原 B 的行号。`cols_g` 表达的是这层关系；局部16列不要求在原矩阵中连续。

例如 U=37 时，三个 K16 的有效列数为16、16、5。**计算缓冲**仍有48个列槽；**GM存储**是否也保存48列，是可以研究的格式选择。稠密补齐 A 为1536 B，去掉尾部11个零列后为1184 B；紧凑列映射从192 B减为148 B。数字只计算 A 值和列映射，不包含目录、描述符及运行时展开成本。

## 3. 当前代码实际具备什么

以下是研究设计时的基线。E0后续已新增独立直装入口、显式就绪/复用同步和guarded runner；设备覆盖与限制见§7.1及[补测总结](../e0-e6-experiments/artifacts/e0-supplement/20261021-r1/summary.md)。

本轮直接检查了以下文件，SHA-256 记录于 [probe-results.json](probe-results.json)：

- `rsh/planner.py` 的 `layout`：窗口列并集排序，生成 `[T,16,16]` FP16 补零块；`cube_ptr` 为窗口块前缀，`colref` 为每块16个原列号，尾槽使用原K作为零行哨兵；另有 `rowmap`。
- `npu/work.h` 的 `CubeWork`：A逐块 ND2NZ→L1，再 LoadData→L0A；B依照16个列索引逐行搬运到L1，再分形内转置到L0B；每次 Mmad 的 m/k 为16。每个K块后有 `PIPE_M` barrier。
- 当前 A 没有运行时 bitmap 解码。L1/L0 输入分配了两份缓冲，但源码没有显式的跨迭代预取日程；“两份缓冲”不能单独证明流水已经充分重叠。

W=16 时 `[Ktile,16,16]` 的 A 字节序已经与所需分形顺序相容，因此“把现有 A 命名为分形格式”不是优化。可检验的变化应是减少搬运指令、减小尾部存储、组织多K16包、改善 B gather，或引入有收益的压缩/展开。

输入目录有8个原始矩阵，已读取形状、存储项数并记录文件哈希。但本项目没有 `results/v2/orders`、`results/d3/plans` 和 `cases_d3` 中的历史冻结计划。**原始CSR存在，不等于给定窗口的实际密度分布已知。** 本轮没有重新生成行重排来替代已确定的窗口；所以不能给出真实窗口的最优密度阈值或预测加速比。

## 4. 候选格式及统一字段

暂称本接口为 **W16 窗口存储协议 v0**，只是工程草案名，不作为新颖性主张。所有整数采用小端；输入索引须在uint32范围内，超出时另设64位版本。

### 4.1 窗口目录和元数据

| 字段 | 类型／长度 | 含义 |
|---|---|---|
| header | 版本、dtype、W、原M/K、G/T、flags | W=16，值为FP16；记录协议版本 |
| win_tile_ptr | uint64[G+1] | 每窗口的tile范围 |
| win_col_ptr | uint64[G+1] | 每窗口有效原列号范围，差值为U_g |
| col_idx | uint32[ΣU_g] | 原A列号＝B行号；按当前基线顺序，窗口内不重复 |
| row_map | int32[G,16] | 沿用固定窗口的原行映射，不能重分组 |
| tile_desc | 每tile 16 B | 见下表 |
| payload | byte数组 | 各tile起点32 B对齐；搬入L0后另满足512 B对齐 |
| run_start_mask（可选） | uint16[T] | 有效列中连续原列号段的起点位图，专用于B搬运 |

每个 `tile_desc` 为 `<QHBBI`：`payload_offset:u64, nnz:u16, kind:u8, valid_k:u8, payload_bytes:u32`。nnz须能表示256；valid_k取1…16，空窗口不生成tile。offset以字节计，payload_bytes不包含末尾32 B对齐空隙。纯稠密对照可采用隐式offset，单独量化引入统一描述符的成本。

`win_tile_ptr[g+1]-win_tile_ptr[g] = ceil(U_g/16)`；tile t 的列映射在 `col_idx[win_col_ptr[g]+16*t : ...+valid_k]`。尾部映射不落盘，kernel通过valid_k补零，不读相邻窗口数据。

### 4.2 四种 A payload

| kind | GM 中的内容 | 还原／装载方式 | 主要用途 |
|---|---|---|---|
| 0 Dense16 | 256个FP16，按[r,k]连续，共512 B | 直接分形复制或保留ND2NZ基线 | 无解码对照，优先优化分组和预取 |
| 3 DenseTail | [16,valid_k]行主序，共32×valid_k B；满块等价Dense16 | ND2NZ时把D方向补到16 | 借鉴ME-BCRS的尾列不落盘思想；不逐非零解码 |
| 1 Bitmap16 | 16个uint16行位图，共32 B；后接按[r,k]递增排列的非零FP16值 | 软件按位图rank填入16×16零底板 | 中等密度候选；须计展开和同步 |
| 2 LocalIndex16 | z个uint8位置p=16r+k；索引区补到偶数字节，再接z个FP16值，共3z+(z mod 2) B | 整段字节流搬至对齐UB，再按局部位置读值、写零底板 | 很低z的对照，避免固定32 B位图 |

Bitmap16 的bit k对应该行局部列k；值流索引为之前所有行的popcount，加本行bit k之前的popcount。省去零的数值编码不会减少 Cube 对这个分形的稠密计算量。v0针对有限FP16数值，零的符号规范化；NaN/Inf及需要保留有符号零的语义另设测试，不从本地有限数值结果外推。

这些编码共享同一列映射。不要为每个非零再存一个原列号，也不要把当前调用的 B 值固化进 A 的长期格式。A结构不变时目录可复用；A值更新时重新编码数值；B每次更新都必须计当次准备成本。

### 4.3 必须成立的不变量

1. 冻结的行映射、窗口边界、Residual归属不变；每个输出行的所有权不变。
2. 每个原非零唯一映射到 `(window,tile,r,k)`，FP16值保持一致；重复CSR项先按既有规范合并。
3. 非尾块valid_k=16，尾块由U推导；padding A/B均为零，任何padding索引不得访问原B界外。
4. bitmap popcount、局部索引项数和descriptor.nnz一致；局部位置递增且无重复；所有偏移和payload长度有边界检查。
5. A和B使用同一局部列顺序。N尾部在片上补齐，仅写回有效特征列。
6. 消费完当前L1/L0槽才能复用；第一个K块清零累加器，之后保留累加，空窗口显式产生零输出。

## 5. 从格式到片上供给

### 5.1 第一条路径：AIC直接消费预展开或紧凑尾块

每个窗口按q个K16分包，q先取1、2、4、8。A包为连续分形；满块批量复制到L1，尾部紧凑块单独ND2NZ。先保持Mmad k=16，以便把包大小和计算粒度的影响分开。

第一版 B 暂存可保持 `[q,Np/16,16(k),16(n)]`：每个K16有独立子视图，沿用当前B装载流程。L0B目标为 `[q,Np/16,16(n),16(k)]`；装载每个分形时转置内部16×16。若改用整块NZ，则B_L1轴序为 `[Np/16,q,16(k),16(n)]`，必须同时改偏移计算。

这里的区别只是布局选择；不能因为逐K16暂存区不等于整块NZ就判定它非法。L1支持自定义暂存布局，最终L0必须满足Cube契约。

后续再单独测试把q个K16合为一次 `Mmad(k=16q)`。A仍按 `[q,16,16]` 装入ZZ；B按上述方式形成ZN。若Load2D的repeat数量超过255，需拆分调用或选适用接口，不能截断计数。聚合K也会增加L0容量需求，并可能改变浮点累加顺序。

### 5.2 B映射如何减少搬运指令

同一K16中，若原列号含连续段，例如 `[2,3,4,19,50,51,…]`，可一次处理相邻B行。静态的 `run_start_mask` 标记每段起点，段终点为下一起点或valid_k；原行首地址从col_idx读取。

对长为ℓ、在本K16内从槽s开始的连续段，可研究一次ND2NZ搬运：源B从该段首行与n_begin开始，`nValue=ℓ, dValue=N_t, srcDValue=B行跨度`，目标从 `s*16` 个FP16处开始，标准单K16暂存的 `dstNzC0Stride=16, dstNzNStride=1`。D尾部补齐；K尾部仍须显式准备零行。

这样可把有效行的搬运调用数由valid_k降到连续段数R；它不保证减少实际HBM读取字节，也不保证数据连续段很多。额外2 B/tile元数据、标量解析和不同API开销必须纳入比较。全离散、部分连续、全连续三类输入都测。

### 5.3 第二条路径：AIV片上展开压缩块

```text
Bitmap/Index值流 GM → AIV UB：清零、解析、填16×16
                                  ↓ UB→TSCM(L1)
当前 B → AIC 准备 B_L1       ready事件 → AIC装载 A_L0/B_L0
                                  ↓ Mmad
                              release事件 → 生产者复用槽
```

建议初版每个AIV处理包内不同的完整tile，避免两个生产者覆盖同一分形。q为奇数或末包不足时，空闲生产者也按相同协议参与mode 2同步。首包、末包和循环次数的ready/release必须配对；L1地址从同一个tiling分配方案导出，不能各核各自分配后假定地址相同。

先做无重叠的正确性版本，再加入双缓冲。解码可从明确的局部位置计算和UB写入开始，再单独优化批量清零与向量化；不假定GPU的warp popcount机制在AIC可用。官方证明UB→L1通路存在，具体共享区初始化、事件时序和目标版本编译仍属E2上机工作。

GM中转版本只用于对照：解码后额外写512 B再读512 B，单次调用全部计时。AIV解码与既有Residual计算的资源竞争必须在完整调用中检查。

## 6. 可复现的存储和供给成本

设一个满K16中有z个非零，暂不计公共列映射和目录：

```text
Dense16 A值 = 512 B
Bitmap16 A值+位图 = 32 + 2z B
LocalIndex16 A值+位置 = 3z+(z mod 2) B（值流保持2 B对齐）
统一协议每tile另有16 B描述符；payload按32 B向上取整。
```

| z（密度） | Dense16 payload | Bitmap payload（对齐后） | LocalIndex payload（对齐后） |
|---|---:|---:|---:|
| 16（6.25%） | 512 | 64 | 64 |
| 32（12.5%） | 512 | 96 | 96 |
| 64（25%） | 512 | 160 | 192 |
| 128（50%） | 512 | 288 | 384 |
| 192（75%） | 512 | 416 | 576 |
| 224（87.5%） | 512 | 480 | 672 |
| 239（93.36%） | 512 | 512 | 736 |
| 256（100%） | 512 | 544 | 768 |

原始payload中bitmap在z<240时少于dense，index在z≤30时少于bitmap、z=31/32时相同；按本协议32 B逐tile对齐后，严格省于512 B的bitmap上界为z=224，许多低z情形的index/bitmap开销也会相同。这些都是**字节阈值**。解码、描述符读取、缓冲和同步决定的**时间阈值**必须实测。

每个K16、Np特征列的当前稠密路径基本量为：A 512 B、B 32Np B、公共满块列映射64 B、稠密计算512Np FLOPs；一个窗口输出写回64Np B。这里只算逻辑搬运量，缓存、事务放大和重复读取须通过profile测量。

| Np | A占A+B输入字节比例（不计元数据） |
|---:|---:|
| 16 | 50.0% |
| 64 | 20.0% |
| 256 | 5.88% |

因此，宽特征下优先压缩A可能触及很小的一部分输入流量；B的聚集成本、搬运调用次数和流水值得与压缩并列研究。此表不能证明B必然是实际瓶颈。

时间选型应比较：

```text
压缩后的A搬运 + 展开 + 跨核同步 + 对其他工作造成的延迟
             与
稠密A搬运
```

存在流水时不能把各阶段孤立耗时直接相加预测总时间，应测包间稳态间隔、首尾开销以及实际AIC等待。总应用成本另含 `A准备/R + 每次B准备 + kernel + 必要写回`，R为A复用次数；B打包不能当作离线免费步骤。

## 7. 实验计划与选择判据

研究设计初稿完成时尚未上机。后续E0及G3独立参照补证已收口；2026-10-22又完成E1四种编码语义：1988主例、720次重复及9小样通过，本地独立回放与归档核验完成，实例已关机。下一项E2，尚未开始。数据见[实验台账](../e0-e6-experiments/experiment-status.md)、[E1总结](../e0-e6-experiments/artifacts/e1/20261022-r1/summary.md)。本轮E1采用含GM中转的串行语义路径，后续阶段定义保持如下：

| 实验 | 固定项与变化项 | 观测／通过条件 |
|---|---|---|
| E0：输入契约微测 | 固定W16；A/B带坐标标签；K=16/32/48，N=16/17/32/33/64；另测官方非整倍数示例 | 对照CPU确认ZZ/ZN、转置、尾部、地址与写回；目标9.0.0编译通过，记录实际资源大小 |
| E1：编码语义 | 同一冻结合成窗口，四种payload；U=0/1/15/16/17/31/32/37/48/63 | **已完成**：全值还原、映射、尾部及Cube输出通过；1988主例+720重复+9小样独立回放通过，最大误差0；含GM中转，不替代E2 |
| E2：展开与交接微测 | bitmap/index；q=1/2/4/8；先单缓冲后双缓冲；关闭Residual | 分别测解码、UB→L1、ready/release；长循环无错配、首尾无死锁；记录资源使用 |
| E3：A格式对照 | 固定B gather、q=1、k=16、同N；比较Dense16/DenseTail/bitmap/index及GM中转对照 | 包含解码与同步的完整AIC支路耗时；GM中转成本不得遗漏 |
| E4：B聚集对照 | 固定A为Dense16；原列全散/部分连续/全连续；逐行搬运 vs 连续段ND2NZ | 测R、指令数、有效字节/实测事务、B准备时间；包括N尾部 |
| E5：包与流水 | 先固定k=16扫q及缓冲级数，再固定q比较k=16与16q；Np=16/32/64/128/256；另对照预排布A从GM直装L0A | 测供给间隔、Cube等待、L1/L0容量；资源超限组合排除并记录原因 |
| E6：冻结真实窗口 | 8个输入的原有行序/路由，AIC/Residual分流相同；选择前述有收益组合 | 报每矩阵及N的完整调用中位数/p95、显存、预处理；含Residual竞争与B准备 |

执行前导入冻结计划并核验原始输入、order、routing、rowmap哈希；缺少这些数据时E6不能用新生成窗口冒充。合成窗口用于隔离机制，不代表真实矩阵密度分布。

计时协议（用于报告性能的实验；E0契约正确性检查不要求性能采样）：每项先预热至少20次；至少5批、每批100次调用，使用设备时间并在测量边界完成必要同步；若调用过短则延长批次到可稳定测量。记录时钟/运行环境、冷热缓存条件、每批中位数及p95、完整样本。profile单独运行，避免其开销混入普通计时。若波动盖过差异，报告无明确收益。

现有 `npu/runner.cpp` 记录的是带stream同步的host完整调用时间，不能直接改名为设备kernel时间；新实验需另加设备事件计时，并保留完整调用计时。任何新增B打包阶段都须进入相应的完整调用计时范围。

数值协议：小整数/二进制分数案例应精确匹配；真实FP16输入以同一FP16 A/B的FP64 CPU参考报告最大绝对误差及按 `sum(abs(A)*abs(B))` 归一化误差。现有runner要求输出有限且逐元素 `abs(error) ≤ 0.01 + 0.01*abs(reference)`，新方案至少通过同一门槛，同时报告完整误差，不能通过放宽阈值掩盖错误。改变K聚合方式时重复检查消去和长归约案例。

选择规则：先通过正确性和资源门槛，再按包含全部供给成本的延迟比较；压缩率只作解释变量。只有真实窗口上收益稳定、完整调用无不可接受回退时才启用压缩；否则保留Dense16/DenseTail。首轮不设未经测量的“密度小于X就用bitmap”规则。混合选择器放在各纯方案测清之后，至少以密度、valid_k、N、包长和AIV竞争为输入，而不是只看z。
