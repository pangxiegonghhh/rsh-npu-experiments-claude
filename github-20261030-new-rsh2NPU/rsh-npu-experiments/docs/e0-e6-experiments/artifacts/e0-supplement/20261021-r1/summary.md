## 两项实现修复和一项构建修复

1. 同一源文件双入口产物中，normal输出仍为初始化标记、device debug为0；direct入口通过。拆分为独立编译单元后两个入口通过。生产代码新增`npu/cube_direct.cpp`，CMake分别编译两个入口。证据限于本工具链和产物，不作CANN普遍限制的结论。
2. GM→L0A直装在多K复用时出现错误；补充M→MTE2复用、MTE2→M就绪事件后，直装扩展与完整调用通过。源码在`npu/work.h`，独立对照在`npu/e0_probe/probe.h`。事件组整体修复有效，未分离两个事件各自的因果贡献；这些同步开销必须纳入后续性能实验。
3. 上传的mtime=0使增量构建保留旧host，输入轮换检查检出了不一致：源码有A轮换，旧产物没有guard_byte元数据，A符号变化未发生。最终全新目录构建后重跑全部223项和复核，实际host元数据/哨兵/轮换均验证。后续不能凭“build返回0”推断源码已进入产物。

首轮507000因缺完整原始上下文，不能唯一追溯其历史原因；本轮以受控对照修复并验证了可用直装路径。各版本失败日志、源码上传包、旧输出均保留在归档，不删除失败结果。

## 资源与边界

GetCoreMemSize返回：L1=**524032**、L0A=65536、L0B=65536、L0C=131072、UB=196352 B。早期屏幕读数524288有误，采用[原始查询](device/resources.txt)。

独立用例最大显式分配：L1合计12800、L0A5120、L0B7680、L0C6144 B。当前生产W16/Np64队列显式分配为L1=5120、L0A=1024、L0B=4096、L0C=4096 B；restore每AIV UB=1024 B。只说明测试组合可合法分配，不推断框架预留或最大可用容量。[地址枚举](address-map.json)、[本地预算检查](local-validation.json)

- L0采用设备选择器观察元素映射，地址采用分配器契约及偏移枚举；没有L0原始字节读回。
- guard与规定零padding分别检查；guard未变不单独证明无越界读。读范围另经枚举和合法区域有限哨兵扰动检查。
- 单次30/70/40采用零填充。未把非零无效归约槽的屏蔽行为当成已验证，也不强制未定义输出padding为零。
- 当前有限FP16合成输入及已列尺寸通过；不外推NaN/Inf、N128/256、真实稀疏窗口或AIV跨核供给。
- E0不提供性能结论。CSV/JSON里的host时间是过程记录，不能用于宣称Cube提速。
