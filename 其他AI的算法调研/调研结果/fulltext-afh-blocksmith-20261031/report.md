## 3. BlockSmith：当前层最直接的补证

### 3.1 它优化什么

论文 §2.2、§4 的核心矛盾与本项目接近：仅按相似性聚类可能形成大小不合适的组，展平成固定高度窗口后又被切开；只做空列压缩，则无法主动改变不合适的行成员。UBT 把相似性、组容量、短组后处理与列压缩连起来，降低实际块数。

这不是“先找几个密集区域”就结束。形成最终排列后，还必须看连续窗口如何切分，以及列压缩后究竟形成多少个块。因此保留当前统一 W16/K16 的独立重算规则，不能用粗特征上的相似度替代 U/T。

### 3.2 可变宽度：每张矩阵选择一种签名粒度

对行 r 的原始列支持集 S_r，用 `floor(j/b)` 的粗列段 ID 构成去重集合 F_b(r)，再计算两份签名的 Jaccard。b=1 是原始列精度，b>1 会把同一列段的不同原列合并成同一特征。这个 b 不是后端列块宽度 K0。

论文式 3 采用 D=max(rows,cols)，一次选定该矩阵的宽度：

| D | b |
|---|---:|
| D<50,000 | 4 |
| 50,000≤D<100,000 | 32 |
| D≥100,000 | 128 |

它不是逐行或每次聚类迭代重新调整宽度。较粗特征可以减少比较成本，但会把原始列不重合的行判成相似；较细特征也不保证贪心聚类结果和总耗时必然更好。上述分段是作者经验规则，不是已经验证适用于 NPU 的普遍规律。

**原文/代码区别。** 缓存作者入口只按 rows 选择宽度，且 rows>200000 会跳过；论文公式用最大维度，附近解释文字还混用了 NNZ 描述。本项目新增 C3-A 明确选择公式的最大维度口径，按原始完整 CSR 形状计算 D，不在去掉空行后改变 D。阈值 K 按 1000 解释，并记录为配置选择。

### 3.3 Iterative clustering 的确切流程

论文算法 1 与 §4.2 给出：

1. 生成各行签名，首行初始化一个组，以首行作为固定代表。
2. 后续行按顺序进入；批量计算它与当前全部活跃组代表的相似度。
3. 活跃组按大小降序遍历，加入**第一个**达到阈值的组，并非相似度最高的组。
4. 组达到 m 行后移出活跃集合；没有合适组时，新行建立新组并成为代表。
5. 更新活跃组大小顺序，继续下一行。

这里的 iterative 指逐行处理和更新活跃集合，不是把所有行反复重新分配直到收敛。固定代表也不是组内列并集或持续更新的质心。

满组退出可以减少后续比较，不能证明最坏近线性：若每行都没有相似组，活跃集合会持续增大，代表比较次数仍可能二次增长。并且当前行的全部代表相似度已经批量计算，首次匹配后的 break 不代表前面的 GPU 批量计算也在首次匹配处停止。完整预处理应继续记录特征生成、传输、排序、后处理和排列物化成本。

### 3.4 阈值、后处理与现有 C3 的差异

| 项目 | 论文 | 已缓存作者代码／本项目 |
|---|---|---|
| 阈值边界 | 算法 1：J>0.2 | 代码 distance≤0.8，对应 J≥0.2；C3 保留代码边界并明确注明。J恰为1/5的行对会受影响 |
| 特征段端点 | 式 1 右端写作闭区间 | 代码按整除分桶；项目采用半开段 `[kb,(k+1)b)`，避免端点重复 |
| 短组后处理 | §4.3 描述大小排序，合并可组成 m 行的短组，余组尾置 | 代码允许大小和≤m继续合并，再整体按大小排序；项目共用 P 有自己的完整组顺序与 tie-break，不是逐行照搬论文 |
| 高度和执行 | 主要结构图/密度对照为8×8，内核含 swap-and-transpose | 项目组容量W16，评价K16；保留来源区别，不把GPU内核一并移植 |

**决定：**不因补读而暗改 C3-W1/W4 已写清的边界、P 或 tie-break。补充配置 C3-A 仅替换宽度选择策略，其他与 C3-W4 相同，便于归因。在 D<50000 的矩阵上，C3-A 与 C3-W4 等价，不当成两个独立结构结果重复计数。

### 3.5 实验能支持什么

论文 §6.5.1 使用 8×8 块比较块数与密度；§6.5.2/表 3 的 14 个代表矩阵中，后处理减少块数的幅度不同，例如 vsp 从 74338 降到 56796（23.60%），wave 从 86268 降到 85930（0.39%）。这是保留指定 P-off 消融的原文依据，不能把这些幅度当成 W16/K16 的预测。

§6.3 明确说明重排开销仍可能是一次 SpMM 的很多倍，更适合静态矩阵重复使用。§6.6 又显示内核优化本身可带来收益，因此论文整体加速不能全部归因为 UBT 或行重排。本项目仍单独测结构和完整预处理成本，后续再验证设备效果。

## 4. AFH：窗口内块构造与路由

### 4.1 原方法怎样组织数据

论文 §3.1–3.3 从固定 16 行窗口出发。每个活跃列 j 具有16-bit行支持签名 sig_j、非零覆盖行数 pop_j 和 Row24 冲突信息。先用高覆盖 seed 贪心构造 Dense 候选，再检查候选占用和移除该候选后的剩余稀疏块代价；接受后，余下列用兼容性和原始列位置邻近性构造 Row24。

图 2 中的 Dense 增益写为：

$$
g_{dense}(j\mid S)=\alpha\,ovlp(sig_j,U(S))+\beta\,pop_j-\gamma\,inc(sig_j,U(S))+\epsilon a_j,
\qquad U(S)=\bigvee_{i\in S}sig_i.
$$

其中 S 是当前候选的列集合，U(S) 是这些列的**行签名按位或**，不是本项目窗口的非空列并集 U_w。图中的稀疏单元匹配则在兼容条件下优先选择中心位置较近的单元。图中文字没有被常规 PDF 文本提取识别，已放大核对。

接受的 Dense 使用16×16块，Row24 使用论文所称16×8压缩/结构化布局；存储保留原始列映射。两条路径在同一 kernel 内共享 B gather 和 C 累加，A 载荷、metadata 和 MMA 不同。算法 1 的两段 loop 顺序处理各类块，不能仅由“fused”推断它证明了本项目的 AIV/AIC 并行方案。

### 4.2 对当前研究目的的帮助

AFH **没有给出跨窗口重新选择行成员的算法**。固定行成员后，重新分组/排列列不会改变该窗原始列并集基数；按本项目单一紧凑 K16 定义计算的 T_w=ceil(U_w/16) 也不会因此自动降低。AFH 改变的是具体块类型、载荷布局、填充、执行路径与费用。

因此将它列为 F-AFH，供后续类 RS-tile/分流层参考：

- 可以借鉴每列在窗口内的行签名来识别不同局部结构。
- Dense 选择不能只看局部密度，还要检查拿走该部分后剩余路径是否更便宜。
- 原始列距离有助于考虑 B gather 的地址局部性，但它与列并集基数是两个指标。
- 实际迁移时应按本项目可实现的 Dense/Bitmap/Index/Residual 路径重新计算供给和执行成本，不能把 GPU 的 Row24 当成 NPU AIV 残余路径或假设存在等价 `mma.sp`。

这是研究层次定位，不是认为 AFH 不值得读，也不是现在启动后续分块实验。

### 4.3 全文仍留下的实现缺口与评价边界

图 2 给出了增益的组成形式，但没有充分给出 alpha/beta/gamma/epsilon、activity/conflict 的完整计算、Dense 占用接受阈值、lookahead 长度及全部尾部处理。正文的伪代码是执行 kernel，而非完整预处理构造伪代码。当前可借鉴流程，不能凭这份正文宣称已拥有忠实复现所需的全部细节。

表 3 还给出一个有用边界：Flan_1565 的混合总块数相对 pure-2:4 **增加4.72%**，同时 Dense 部分的局部密度提高。不同块类型的数量不能不分成本简单相加后当作性能排名；更不能将 AFH 的混合块数直接替代本项目统一 K16 指标。

论文 GPU 性能主表使用各 baseline 的成功共同覆盖子集，三模式消融的公共集合为584项，不能假定每一个比较都完整覆盖600项。预处理降低幅度与显存节省也只支持原文指定矩阵/平台，不是本项目结果。
